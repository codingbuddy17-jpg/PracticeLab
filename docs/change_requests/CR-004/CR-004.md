## 1. Why

The text view's section bookmarks found **3 of 17 sections** on an ordinary 3-page H&P. Measured with the viewer's own code, there were four causes:

1. It kept only the **first heading on each page**, so a page held at most one bookmark.
2. It kept each section name **once per chart**, so a chart with an H&P, progress notes and a discharge summary showed one Assessment & Plan.
3. **"SOCIAL HISTORY: former smoker"**, a heading with its content on the same line and the most common way an EHR prints a short section, was read as a label/value field.
4. Any line *starting* "Plan…", "Assessment…" or "Exam…" became a heading.

Bookmarks also jumped to the page rather than the section.

## 2. What changes

| | Before | After |
|---|---|---|
| Sections on the sample H&P | 3 | **15 of 15** |
| 4-page chart, 3 notes | ≤ 4 bookmarks, one per page | **24 sections in 3 documents** |
| Bookmark target | the page | the exact heading |
| Organisation | a flat row of chips | a **navigator**: documents (H&P, Progress Note, Consult, Operative Report, Discharge Summary, ED Note, Radiology, Pathology…), each listing its sections in order, with page numbers |
| Where am I | — | the navigator highlights the section being read as the reader scrolls |
| Views | Image · Text | Image · Text · **Side by side** (scan beside its text, kept on the same page) |
| Note styling | headings and fields | document bands, section bands showing the chart's own wording, aligned label/value fields, numbered and bulleted lists, muted signature lines, wrapped PDF lines rejoined |
| Coding aids | — | optional highlight of **uncertain-diagnosis** wording (probable, suspected, rule out, consistent with…) and **linkage** wording (due to, secondary to, associated with…). **Off by default**, a per-reader toggle, remembered |
| Keyboard | ← → pages, Ctrl+F, Esc | plus **Alt+↓ / Alt+↑** next/previous section and **/** to search |
| Reopening a chart | always Image, top | the reader's last mode and section |

Image mode, thumbnails, zoom, in-chart search and flagging a chart issue are unchanged.

## 3. Rules (for anyone extending the vocabulary)

In `frontend/src/components/chartDocument.ts`:

- A line is a **section heading** when one of these holds:
  - the whole line is a known section name, optionally with a trailing colon (outline markers like `I.` or `1)` are allowed);
  - it's a known name, a colon, then content (the content becomes the section's first line);
  - it's an ALL-CAPS line of up to 6 words ending in a colon (kept under its own wording).

  A sentence that merely starts with a section word is never a heading.
- A line is a **document title** when it ends in a known document name (an optional trailing date is allowed) and is shaped like a title: ALL CAPS or Title Case. A one-word name standing alone ("ORDERS") must be ALL CAPS.
- A line starting in lower case continues the prose or list item before it.
- Coding-aid patterns are generic wording and never drawn from an answer key, so highlighting gives nothing away.

## 4. Verification

- Parser measured on sample charts, including 17 trick lines ("Plan to discharge tomorrow", "Exam was unremarkable", "Please see progress note"…). None of them became a heading or document.
- Browser-tested at 1366×900 and 1920×1080 on a generated 4-page PDF going through the real PyMuPDF extraction. Checked: jumps and Alt+↑ highlight the right section, manual scrolling is tracked, side by side follows the page, a reload restores mode and section, **no page is clipped, nothing overflows, no console errors**.

## 5. Not included

**Text for scanned or image-only charts.** Text comes from a PDF's embedded text layer, so scans have none. The viewer now says so and points to Image and Side by side. OCR is backlog item B-002.
