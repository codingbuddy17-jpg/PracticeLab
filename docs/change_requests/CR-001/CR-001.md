# CR-001 — Practice review shows right as well as wrong; E/M review classified; Excel export

| | |
|---|---|
| **Kind** | C (backend + frontend). No schema change |
| **Module** | PracticeLab (coder module): post-submit review |
| **Affects** | Trainer **Review** modal (batch → practice sessions → Review) and the coder's results screen |
| **Order for IT** | **Backend first, then the frontend patch.** The frontend reads a new `review` field and calls two new routes. Applying the patch to a backend without them leaves the review blank and makes the export button fail |
| **Commits** | `db51300` (feature) · `f6198ef` (E/M Diagnoses as one section; schema-guard fixes) |
| **Status** | Built and verified in the original app. Not yet implemented in .NET |

---

## 1. What users saw

1. **The review showed only what was wrong.** After submission, the review listed the codes that lost points. A trainer couldn't see what the coder got right, so the review wasn't complete.
2. **The E/M and ED Profee review wasn't classified.** In the trainer's Review modal these charts went through the IP/OP layout. They showed "PDx submitted: —" and a flat list of score lines, with no Primary Dx / Secondary Dx / CPT / E/M level / reasoning sections.
3. **E/M reasoning scores such as 6.7 of 10 couldn't be explained.** The score was correct (see §3), but the screen never showed the elements behind it.
4. **There was no export.** The review couldn't be copied out or kept.

## 2. What changes

Every graded chart in a review now carries a **`review`** object: every line from the answer key and from the coder, side by side, grouped into sections, each line marked with a result. Both screens render it. A new **Export to Excel** button downloads the same content as a formatted workbook.

| Specialty | Sections, in order |
|---|---|
| IP-DRG, SDS, Surgery, ED Facility, ED Single Path, Ancillary | Principal Diagnosis · Secondary Diagnoses · Procedures (ICD-10-PCS) · CPT / HCPCS. Only sections where the key or the coder has something |
| **E/M, ED Profee** | *Coding:* E/M Level · Diagnoses (Primary Dx row, then Secondary Dx rows) · CPT / Procedures. *Reasoning:* Problems Addressed (COPA) · Data Reviewed and Analysed · Risk of Patient Management, **element by element**. A time-levelled chart shows a **Time** section instead of the three MDM tables. A visit not graded on MDM (preventive etc.) shows one note saying so |
| Edits, Denials | Responses (Review / Research / Resolution / Final Rationale) with the trainer's rubric verdict once scored |

**This is display only. No score changes.** Points come from what grading already stored. The comparison rules below match the grader's own rules, so a line is never marked wrong when the score counted it right.

## 3. Business rules (implement these exactly)

### 3.1 Result values

| `status` | Meaning | Shown as |
|---|---|---|
| `correct` | In the key and coded the same | ✓ Correct |
| `missed` | In the key, not coded | ✗ Missed |
| `extra` | Coded, not in the key | + Extra (not in key) |
| `different` | Both present, but a detail differs | ≠ Differs |
| `info` | Context, not judged (e.g. total time, Edits/Denials text before scoring) | (no badge) |

`summary` counts `correct`, `missed`, `extra` and `different` across all rows of the chart. `order` and `info` are not counted.

### 3.2 Comparing codes

- Codes are compared **without dots and case-insensitively** (`E11.9` = `e119`).
- A list (SDx, PCS, CPT, E/M Dx) is compared as a **multiset**. Each key line pairs with the **first unused** coded line that has the same code. Unpaired key lines are `missed`, and unpaired coded lines are `extra`.
- A paired line is `different` instead of `correct` when:
  - **SDx:** the key states a POA and the coded POA differs. Note: `POA: key Y, coded N`.
  - **CPT:** the modifier differs (note `Modifier: key 59, coded (none)`), **or** the key states units and the units differ (note `Units: key 2, coded 1`). Units are judged only when the key states them, which is the grader's rule.
- **PDx:** both present and equal → `correct`. Both present and unequal → `different`. Key only → `missed`. Coder only → `extra`.
- A line displays as the code followed by `POA x`, `mod x`, `xN` (units, only when not 1) and `ptr a,b`, separated by two spaces.

### 3.3 E/M Level section (rows only where a side has a value)

| Row | Key field (`em_answer_keys`) | Coder field (`practice_chart_drafts.em_data`) | Rule |
|---|---|---|---|
| E/M code | `em_code` | `em_code` | equal → correct, else different |
| Modifier | `em_modifier` | `em_modifier` | upper-case compare |
| Patient type | `patient_type` | `patient_type` | shown unless both are blank or `NA` |
| Levelled by | `level_method` (default `MDM`) | `level_method` (default `MDM`) | **always shown**. When they differ, note: *Reasoning points are not earned on the wrong route* |
| Critical care minutes | `critical_care_minutes` | `critical_care_minutes` | shown when either side has a value |

Points: from the stored feedback line `E/M Level: x/y pts`.

### 3.4 E/M diagnoses — ONE section, because they are ONE scored component

> **Superseded by [CR-002](../CR-002/CR-002.md) §4**, which makes the primary diagnosis a scoring factor. Implement CR-002's version. This section records what CR-001 shipped.

E/M Dx scoring is order-blind: `(key codes coded anywhere ÷ key codes) × Dx weight`, minus an over-coding penalty. **The primary diagnosis carries no separate score, and order costs nothing.** The section is shaped so that it can't read otherwise:

- One section, `key: "dx"`, title **Diagnoses**, points from `Dx: x/y pts`.
- Section note: `Scored as a set: m of n key diagnoses coded[, k over-coded]. Order, including which is listed first, is not scored.` If the key lists no diagnoses: `The key lists no diagnoses, so this component earns full credit.`
- **Primary Dx row**: the key's first code.
  - If the coder coded it first → `correct`.
  - If they coded it at a later position → **`correct`**, with the note `Coded at position N, not first. Order is not scored on E/M`.
  - If they didn't code it → `missed`.
- **Secondary Dx rows**: the key's remaining codes, compared as a multiset (§3.2) against the coder's list minus the code the Primary row used.

The first version showed `order` beside the Dx points and read as a deduction for order, which the grader never makes. Don't reintroduce it.

### 3.5 E/M reasoning — one section per MDM table, element by element

The three tables and their elements, in the grader's order:

| Table | Elements |
|---|---|
| COPA | `copa_self_limited` `copa_stable_acute` `copa_stable_chronic` `copa_acute_uncomplicated` `copa_chronic_exacerbation` `copa_undiagnosed_new` `copa_acute_systemic` `copa_acute_complicated_injury` `copa_chronic_severe` `copa_threat_to_life` |
| Data Review | `dr_prior_external_notes`* `dr_review_test_results`* `dr_order_tests`* `dr_independent_historian` `dr_independent_interpretation` `dr_external_discussion` |
| Risk | `risk_low` `risk_prescription_drug_mgmt` `risk_minor_surgery_with_factors` `risk_elective_major_no_factors` `risk_hospitalization` `risk_sdoh` `risk_drug_intensive_monitoring` `risk_elective_major_with_factors` `risk_emergency_major_surgery` `risk_hospitalization_escalation` `risk_dnr_deescalate` `risk_parenteral_controlled` |

\* a **count**, not yes/no. Display labels are in `backend/services/practice_review.py → ELEMENT_LABELS` (the wording on the coder's form).

For each element where the key or the coder is non-zero:

| Key | Coder | Status | Note |
|---|---|---|---|
| non-zero | equal to key | `correct` | |
| non-zero | non-zero, different (counts) | `different` | *Count must match the key exactly* |
| non-zero | zero | `missed` | |
| zero | non-zero | `extra` | *Not penalised* |

Values display as `Yes`/blank for yes/no elements and as the number for counts.

**The first row is the table's Level:** key = `em_answer_keys.copa_level` / `dr_level` / `risk_level`, coder = the level derived from their ticks (stored on the feedback line). Equal → correct, else different. Note: *Derived from the elements below*.

**Section note** (this is what explains the 6.7):
- key ticked `n > 0` elements, coder matched `m`: `Matched m of n element(s) the key expects. Points = m/n x <weight>`
- key ticked none: `The key expects no elements here, so this table earns full credit.`
- the coder levelled by the other route: `Levelled by TIME instead of MDM — reasoning points not earned.`

Points: from the stored feedback lines `COPA (…) — x pts`, `Data Review (…) — x pts`, `Risk (…) — x pts`. Max: the chart's applied weight for that table (normally 10).

**The grading rule being displayed, unchanged** (`em_grading.py → _element_score`):
`table points = (key elements the coder matched exactly ÷ elements the key ticked) × table weight`.
Only elements the key ticked count. Extra ticks cost nothing. A count must match exactly. Key ticks 3, coder matches 2 → 2/3 × 10 = **6.67, shown as 6.7**.

**Time-levelled key** (`level_method = TIME`): one *Time* section with a `Total time (minutes)` row (status `info`). Points from `Time supports the level — x pts`. Note: *Levelled by time: full credit for the time route with time in band, half for the right route with time out of band.*

**Not graded on MDM** (the category folds reasoning into coding): one *Medical Decision Making* section with no rows and the note *Not assessed on MDM for this kind of visit; its weight is folded into the coding score.*

## 4. API contract

### 4.1 New field on existing responses (not visible in OpenAPI — see §7)

Each chart object gains `review`, on all three routes that already return chart results:

- `GET /practicelab/practice-sessions/{session_id}/review` → `charts[].review`
- `POST /practicelab/practice-sessions/{session_id}/submit` → `results[].review` (when results are shown)
- `GET /practicelab/practice-sessions/by-token/{token}` → `results[].review` (submitted and released)

```json
"review": {
  "sections": [
    {
      "key": "copa",                       // pdx|sdx|pcs|cpt (IP/OP) · em_level|dx|cpt|copa|dr|risk|time|mdm (E/M) · ed
      "title": "Problems Addressed (COPA)",
      "group": "Reasoning",                // "Coding" | "Reasoning"
      "points": 6.7,                       // number | null
      "max_points": 10.0,                  // number | null
      "note": "Matched 2 of 3 elements the key expects. Points = 2/3 x 10",   // string | null
      "rows": [
        {"item": "Level", "key": "Moderate", "coded": "Moderate", "status": "correct", "note": "Derived from the elements below"},
        {"item": "Undiagnosed new problem (Moderate)", "key": "", "coded": "Yes", "status": "extra", "note": "Not penalised"}
      ]
    }
  ],
  "summary": {"correct": 9, "missed": 2, "extra": 1, "different": 2}
}
```

All strings are non-null (empty string when absent). The section order is as listed in §2.

### 4.2 New routes

| Method · path | Returns | Errors |
|---|---|---|
| `GET /practicelab/practice-sessions/{session_id}/review/export` | `.xlsx` (trainer) | 404 no session · 400 not submitted |
| `GET /practicelab/practice-sessions/by-token/{token}/review/export` | `.xlsx` (coder's own) | 404 unknown token · 400 not submitted · **403 results not released** (`show_results_to_coder` false) |

Both answer at `/api/...` as well. Headers: `Content-Type: application/vnd.openxmlformats-officedocument.spreadsheetml.sheet`, `Content-Disposition: attachment; filename="PracticeReview_<coder>_<session_id>.xlsx"`. `<coder>` is the coder name with every non-alphanumeric character replaced by `_`.

**The coder route must not leak results.** It is gated exactly as the results screen is. A coder whose trainer hasn't released results must get 403, not a file.

### 4.3 The workbook

| Sheet | Columns | Content |
|---|---|---|
| **Summary** | Coder · Specialty · Submitted · Chart · Score % · Result · Correct · Missed · Extra · Differs | One row per chart. Result cell is green for PASS, red for FAIL |
| **Review** | Chart · Score % · Section · Points · Item · Answer key · Coded · Result · Note | One row per review row. Points (`x / y`) only on a section's first row. The section note is prefixed to the first row's note, joined by ` \| `. A section with no rows gets one row carrying its note. Result cell coloured: Correct green · Missed red · Extra orange · Differs amber |

Both sheets: navy header row, frozen header, autofilter, column widths fitted to content. Note column 60 wide, wrapped.

## 5. Database

**No change.** Reads only:
- `practice_results` (as before)
- `practice_chart_drafts.em_data` (TEXT, JSON: the coder's E/M form)
- `em_answer_keys` (`SELECT *` per E/M chart: element columns, levels, `em_code`, `em_modifier`, `patient_type`, `level_method`, `total_time`, `critical_care_minutes`, `em_category`)

## 6. Acceptance tests

Executable against the .NET deployment, with any submitted session id from your environment:

```bash
python3 scripts/smoke_deployed.py --base https://<your-api> --session <submitted session id>
```

It checks that every chart carries a classified `review` with valid statuses and a summary, that E/M MDM sections explain their points, and that the export is an `.xlsx`. Pick an **E/M** session to exercise the reasoning checks.

The worked case to reproduce by hand, which `backend/tests/test_practice_review.py` pins:

| | Key | Coder |
|---|---|---|
| E/M code | 99214 | 99214 |
| Dx | E11.9, I10, J45.909 | I10, E11.9 |
| COPA | stable chronic, chronic w/ exacerbation, acute uncomplicated | stable chronic, chronic w/ exacerbation, undiagnosed new |
| Test results reviewed | 2 | 3 |
| Risk | prescription drug mgmt | prescription drug mgmt |

Expected: Diagnoses **23.3 of 35**, note `Scored as a set: 2 of 3 key diagnoses coded…` · Primary Dx E11.9 `correct` (note: position 2, not scored) · Secondary I10 `correct`, J45.909 `missed` · COPA **6.7 of 10**, note `Matched 2 of 3 …`, acute uncomplicated `missed`, undiagnosed new `extra` *Not penalised* · Data Review **0.0 of 10**, test results `different` (2 vs 3) · Risk 10.0 of 10 · summary `{correct 10, missed 2, extra 1, different 2}`.

Also:
1. A released session's coder export returns 200. An unreleased one returns **403**. An unsubmitted one returns 400.
2. A time-levelled E/M chart shows a *Time* section and no COPA/Data/Risk sections.
3. An ED Profee chart shows the E/M layout (first section is E/M Level).

## 7. Notes for IT

- **`openapi.diff.txt` shows only the two new routes.** The `review` field added to three existing responses doesn't appear there, because those routes return untyped objects. Treat §4.1 as the contract for that field.
- **Frontend:** `frontend.patch` applies to the unchanged React frontend with `git apply`. It adds `components/SubmissionReview.tsx` and edits `PracticeSession.tsx`, `practicelab/BatchDetailView.tsx`, `api/practicelabApi.ts` and `api/download.ts`.
- **Reference implementation (Python), for reading, not porting:** `backend/services/practice_review.py` (the whole builder and the workbook), wired in `routers/practicelab_pkg/practice_sessions.py → _build_coder_results` and the two export routes. `em_grading.py` only moved the three element lists to module constants (`COPA_FIELDS`, `DR_FIELDS`, `RISK_FIELDS`). Grading behaviour is unchanged.
- **One known edge:** the review reads the *current* E/M key. If a trainer edits a key after grading and doesn't re-grade, the element rows reflect the new key while the points reflect the old grading. **Re-grade** realigns them.

## 8. Risk and rollback

- Read-only, with no score or schema change. Rollback is removing the field and the two routes.
- Cost: one extra key read per E/M chart in a review, which is negligible at review sizes.

## 9. Out of scope

- **The scoring rule itself.** Extra elements unpenalised, exact count match and proportional credit are intended and unchanged. Changing them would move existing scores and needs its own CR.
- PDF exports, analytics, and the auditor module.
