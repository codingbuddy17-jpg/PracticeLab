# CR-007 — A same-family code is a wrong code, not a miss

| | |
|---|---|
| **Kind** | C (backend + frontend). No schema change |
| **Module** | PracticeLab grading feedback · review screen and export · analytics that read feedback |
| **Commit** | `78256e8` |
| **Score impact** | **None.** Scores are computed from exact matches before this runs. Only how an unmatched code is *classified and shown* changes |
| **Order for IT** | Backend first, then the frontend patch |

## 1. Why

When a coder entered **Z77.9** for a key's **Z77.8**:
- the feedback said **"Missed Z77.8"**;
- **Z77.9 appeared nowhere**, unless the coder had also entered more codes than the key holds, in which case it was buried in an over-coding note.

That reports a specificity slip as an omission and hides what the coder actually did. Only PDx ever produced "Wrong code". SDx, PCS and CPT never did.

## 2. The rule

After exact matching, each **unmatched key code** is paired with an **unmatched coder code of the same family**. If there are several candidates, it takes the one sharing the longest prefix.

| Kind | Same family means |
|---|---|
| ICD-10-CM (PDx, SDx) | same 3-character category (Z77.8 / Z77.9, E11.22 / E11.9) |
| ICD-10-PCS | same first 3 characters: section, body system, root operation |
| CPT / HCPCS | same first 4 characters (99214 / 99213) |

- A pair is reported as **`Wrong_Code`**, with `ak_code` = the key's code, `coder_code` = the coder's code, and `detail`:
  - ICD-10-CM: `Same category Z77 — wrong code (specificity)`
  - PCS: `Same root operation — differs at character 5 (approach)`. Every differing position is named: 4 body part, 5 approach, 6 device, 7 qualifier
  - CPT: `Same code family — wrong code`
- An unmatched key code with no same-family partner stays **`Missed`**.
- A paired coder code is no longer listed as surplus in the over-coding note. The **over-coding count is unchanged**, because it's count-based.
- Applies to the IP SDx, OP SDx, PCS and CPT matchers (`grading_engine.py → _report_unmatched`). PDx already reported Wrong_Code.

## 3. Review screen and export

The review builds the same pairing from the stored code lists, using the grader's own function, so the screen and the feedback agree:
- a new row status **`wrong`**, shown as **✗ Wrong code**, with the detail above as its note;
- `summary` gains **`wrong`**; the workbook's Summary sheet gains a **Wrong code** column, and wrong rows are coloured as errors;
- the IP PDx and the E/M primary diagnosis show `wrong` (previously `different`) when the code differs.

Because the review is computed from the stored lists, **past sessions show the new classification immediately**. Stored feedback, and so analytics, changes for **new and re-graded** sessions only.

## 4. Knock-on effects (intended)

- "Most missed codes" lists stop counting near-misses as misses.
- **Specificity Drops** analytics only ever counted `Wrong_Code` rows, so it only saw PDx. It now covers secondary diagnoses too.
- The smoke script accepts the `wrong` status.

## 5. Acceptance tests

`backend/tests/test_practice_review.py`:
- Z77.8 → Z77.9 is one `wrong` row, noted "Same category Z77";
- Z77.8 → N39.0 stays `missed` + `extra`;
- PCS 0DTJ4ZZ → 0DTJ0ZZ is `wrong`, noted "character 5 (approach)";
- grader feedback carries `("SDx", "Wrong_Code", "Z77.8", "Z77.9")` and no Missed;
- CPT 99214 → 99213 is Wrong_Code while 36415 stays Missed;
- OP SDx E11.22 → E11.9 is Wrong_Code;
- **a near miss and an unrelated code score identically.**

Verified in the browser: the trainer review shows "1 wrong code", the row reads Z77.8 · Z77.9 · ✗ Wrong code, and a genuine miss and extra on the same chart are still shown as such.
